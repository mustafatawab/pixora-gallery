# Environments: local vs cloud

Pixora uses **two separate Supabase projects**:

| | Local (development) | Cloud (staging / production) |
|---|---|---|
| Runs on | Docker on your machine | Supabase hosted |
| URL | `http://127.0.0.1:54321` | `https://<project-ref>.supabase.co` |
| Database | Postgres in Docker, port `54322` | managed Postgres |
| Data | disposable, reset anytime | persistent |
| Keys | generated by the CLI | dashboard → Project Settings → API |
| Credentials in git | never (`.env.local` is ignored) | never (host env vars) |

Develop and test against **local**; deploy migrations to **cloud**. Do not develop
day-to-day against production data.

---

## 1. Local stack (what Phase 0/1 created)

`bun run db:start` asks the Supabase CLI to launch a set of Docker containers:

| Container | Purpose | Port |
|---|---|---|
| `supabase_db_pixora-gallery` | Postgres | `54322` |
| `supabase_kong_pixora-gallery` | API gateway (REST/Auth/Storage) | `54321` |
| `supabase_studio_pixora-gallery` | Supabase Studio UI | `54323` |
| `supabase_inbucket` / `mailpit` | local email inbox | `54324` |

This **is** a real Supabase instance, just local. It is not pgAdmin and it is not
your cloud project. You can open Studio at http://127.0.0.1:54323.

### Where the keys came from

`supabase start` printed a block like:

```json
{"API_URL":"http://127.0.0.1:54321",
 "ANON_KEY":"eyJhbGciOiJIUzI1NiIs...",
 "SERVICE_ROLE_KEY":"eyJhbGciOiJIUzI1NiIs..."}
```

Those are the local keys. They are derived from the CLI's fixed local JWT secret
(`super-secret-jwt-token-with-at-least-32-characters-long`), are the same for
every Supabase local install, and are safe **only** on localhost. I copied them
into `.env.local` (gitignored), mapping:

```
ANON_KEY         -> NEXT_PUBLIC_SUPABASE_ANON_KEY
SERVICE_ROLE_KEY -> SUPABASE_SERVICE_ROLE_KEY
API_URL          -> NEXT_PUBLIC_SUPABASE_URL
```

Re-print them any time with:

```bash
bunx supabase status -o env
```

### Lifecycle

```bash
bun run db:start     # start / resume containers (data persists in a Docker volume)
bun run db:stop      # stop containers, keep data
bun run db:reset     # DROP + re-apply migrations + seed (destroys local data)
```

The seeded users (`demo1@example.com` / `demo2@example.com`, password
`password123`) exist only locally.

### Optional: browse the local DB with pgAdmin4

pgAdmin4 works fine against the local Postgres:

```
host=127.0.0.1 port=54322 user=postgres password=postgres database=postgres
```

But for schema changes use **migrations**, not manual SQL in pgAdmin — otherwise
local and cloud drift.

## 2. Cloud project

You already have a hosted project. Use it for staging/production, and create a
second project later if you want a separate staging environment.

### Get the credentials

Supabase dashboard → your project → **Project Settings → API**:

| Dashboard value / source | `.env` variable | Exposure |
|---|---|---|
| Project URL | `NEXT_PUBLIC_SUPABASE_URL` | public |
| Publishable key (`sb_publishable_...`) **or legacy `anon` JWT** | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | public |
| Secret key (`sb_secret_...`) **or legacy `service_role` JWT** | `SUPABASE_SERVICE_ROLE_KEY` | **server only** |
| Generate with `openssl rand -hex 32` | `CRON_SECRET` | **server only** |
| Project ref | (CLI only) | not secret |

Notes:

- New projects use **publishable/secret** API keys. `@supabase/ssr` and
  `supabase-js` accept the publishable key wherever the anon key was used.
- Legacy `anon` / `service_role` JWTs still exist under **Legacy API keys** and
  are what our local stack uses.
- The **secret/service_role key bypasses RLS**. It must never appear in a
  `NEXT_PUBLIC_*` variable, client component, or browser bundle. It is only for
  admin tasks (cleanup jobs, seeding).
- Never paste production keys into chat, issues, or committed files.

### Push the schema

Migrations already in `supabase/migrations/` are the source of truth.

```bash
bunx supabase login                     # once, opens browser
bunx supabase link --project-ref <ref>  # ref from dashboard -> Project Settings -> General
bunx supabase db push                   # applies pending migrations
```

If the cloud project already has the old v0 tables (`profiles`, `images`,
`gallery-images` bucket from `scripts/`), `db push` will conflict. Options:

1. **Recommended for a fresh product DB:** back up anything you need, drop the
   old tables/bucket in the SQL editor, then `db push`.
2. Or baseline the existing schema (`supabase migration repair`) if you
   intentionally want to keep it.

Do the same for Storage: migration `20251124000001_storage.sql` creates the
private `media` bucket and policies. Migration `20251124000003_hardening.sql`
adds `images.thumbnail_path`, restricts anonymous reads to public thumbnails,
creates the paginated feed RPC, and adds the upload-quota table/function.

### Auth URL configuration (needed for Phase 2)

Dashboard → **Authentication → URL Configuration**:

- **Site URL:** `https://your-domain.com` (or `http://localhost:3000` while
  testing against cloud)
- **Redirect URLs:** add `https://your-domain.com/auth/callback` and the local
  equivalent if needed.
- Enable **email confirmations** for production (locally they are off).
- Configure SMTP if you do not want Supabase's default email limits.

### Orphan cleanup (Phase 3)

Uploads go directly from the browser to Storage. If a browser closes between the
upload and the metadata Server Action, the object has no `images` row. The daily
cron at `GET /api/cron/cleanup-orphans` removes those objects once they are older
than 24 hours.

Set both on the host:

- `SUPABASE_SERVICE_ROLE_KEY` — the job needs it to scan the bucket and bypass RLS.
- `CRON_SECRET` — a random value (`openssl rand -hex 32`).

`vercel.json` schedules the job at 03:00 UTC; Vercel automatically sends
`Authorization: Bearer $CRON_SECRET`. On another host, schedule the same request
yourself. Without `CRON_SECRET` the endpoint returns `503`; with a wrong or
missing bearer token it returns `401`. The same job also prunes upload-quota
events older than 7 days.

### Phase 5 hardening (thumbnails, quota, headers)

- **Thumbnails/EXIF:** the browser encodes a bounded WebP (JPEG fallback) before
  upload. Canvas re-encoding strips EXIF/GPS. The `media` bucket stays private;
  anonymous reads are allowed only for `images.thumbnail_path`, so originals are
  never publicly signable. Rows created before this migration have no thumbnail;
  visitors see "Preview unavailable" until they are re-uploaded.
- **Upload quota:** `consume_upload_quota` allows 30 uploads per rolling hour.
  It is a security-definer function with a hard-coded limit; do not expose a
  caller-supplied limit.
- **Headers/CSP:** set in `next.config.mjs`. HSTS is sent when `VERCEL=1` (set by
  Vercel) or `ENABLE_HSTS=true` (other HTTPS hosts). Leave it unset for local
  HTTP so Chrome does not upgrade localhost to HTTPS.
- **Bundle scan:** run `bun run check:client-secrets` after every production
  build. It fails on service-role keys/JWTs, `CRON_SECRET`, private key material,
  and suspicious `NEXT_PUBLIC_*` names.
- **CI:** `.github/workflows/ci.yml` starts local Supabase, resets/seeds, runs
  lint + all Vitest suites + build + secret scan, then runs the browser smoke
  suites against `next start`.

### Generate types from cloud

```bash
bunx supabase gen types typescript --linked --schema public > lib/types/database.ts
```

(`bun run db:types` targets the local stack.)

## 3. Which env file wins?

Next.js load order (later wins):

1. `.env`
2. `.env.local` (always wins for local runs; gitignored)
3. `.env.development` / `.env.production`

For deployments, set variables in the host (Vercel → Project → Settings →
Environment Variables) instead of committing files. Production builds should
**never** read `.env.local`.

Suggested setup:

| File | Points at | Committed |
|---|---|---|
| `.env.example` | placeholders | yes |
| `.env.local` | local stack | no |
| host dashboard env | cloud project | n/a |

For tests, keep them pointed at local. Override explicitly if needed:

```bash
SUPABASE_URL=http://127.0.0.1:54321 \
SUPABASE_ANON_KEY=... \
SUPABASE_SERVICE_ROLE_KEY=... \
bun run test:rls
```

Never run the RLS suite against production.

## 4. Safety checklist

- [ ] `.env.local` is gitignored (it is; `.env*` with a `!.env.example` exception).
- [ ] Service-role/secret key is only in server-side env vars.
- [ ] `CRON_SECRET` is set and differs from local development.
- [ ] RLS is enabled on every table that is exposed through the API.
- [ ] Migrations — not manual dashboard edits — are how schema reaches cloud.
- [ ] Auth redirect allow-list contains only real domains.
- [ ] `db:reset` is never pointed at a cloud project.
- [ ] `bun run check:client-secrets` passes on the deployed build.
- [ ] HSTS is enabled on the HTTPS host (`VERCEL=1` or `ENABLE_HSTS=true`).
- [ ] `curl -I` shows the CSP and security headers in production.
